## 第 2 页｜结论先行：先说最终答案

**内容**
- 对大多数研发团队来说，最佳实践通常不是“只买一个工具/只用一个模型”，而是：
  - **1 个主工作台**
  - **1 个日常主力模型**
  - **1 个复杂任务模型**
  - **1 个低成本高吞吐模型**
- 当前较稳的结论：
  - **主工作台默认优先：Cursor**
  - **复杂长链路任务补充：Claude Code**
  - **国内企业治理 / 合规 / 知识库场景优先评估：CodeBuddy**
  - **低成本试点/预算敏感：Trae**
  - **开源自控 / 自带模型 / 本地模型优先：OpenCode**
- 模型层建议：
  - **日常主力**：Claude Sonnet 4.6
  - **复杂规划/重构攻坚**：Claude Opus 4.6
  - **复杂工程第二视角 / agentic coding**：GPT-5.3-Codex
  - **超大上下文**：Gemini 2.5 Pro
  - **低成本高吞吐**：Gemini 2.5 Flash / MiniMax M2.5
  - **中文业务与国内团队**：GLM-5-Code

**辅助图建议**

  - 横轴：成本
  - 纵轴：综合产出
  - 不同颜色区分“日常主力 / 攻坚 / 降本 / 中文场景”

## 第 3 页｜我们日常开发流程里，AI 真正能提效的环节

**内容**
- 从日常研发流程看，AI 主要能介入 7 个环节：
  1. **需求理解**：PRD、接口文档、历史方案快速摘要
  2. **方案设计**：任务拆解、接口草案、边界条件梳理
  3. **编码实现**：函数生成、补全、多文件修改、样板代码生成
  4. **调试修复**：读报错、定位根因、给修复路径
  5. **测试补齐**：单测草稿、mock、边界用例、回归检查点
  6. **Code Review**：发现风险点、命名/结构问题、潜在回归
  7. **文档沉淀**：README、变更说明、交接文档、复盘记录
- 真实经验上，AI 最容易快速见效的不是“完全替代开发”，而是：
  - 提高首版产出速度
  - 缩短信息收集时间
  - 缩短 bug 定位时间
  - 降低重复劳动

**辅助图建议**
- 流程图：需求 -> 设计 -> 编码 -> 调试 -> 测试 -> Review -> 文档
- 每个节点下标注“AI 典型动作”和“提效方式”

## 第 4 页｜先把问题拆开：工具层和模型层不是一回事

**内容**
- **工具层（工作台）** 解决的是“怎么协作更顺手”：
  - 是否在 IDE 内完成
  - 是否支持 diff、补全、上下文管理
  - 是否支持 agent 自动跑命令/改文件/修 bug
- **模型层（大模型）** 解决的是“谁更擅长做什么”：
  - 写代码质量
  - 长上下文理解
  - 中文需求转代码
  - 结构化输出
  - 成本和速度
- 所以做团队选型时，不应该问：
  - “哪个最强？”
- 而应该问：
  - “哪个工作台最适合我们的协作方式？”
  - “哪个模型组合最适合我们的任务结构？”

**辅助图建议**
- 双层架构图：
  - 上层：Cursor / Claude Code / Trae / CodeBuddy / OpenCode
  - 下层：Sonnet / Opus / GPT / Gemini / GLM / MiniMax
- 页脚加一句：`工具决定体验，模型决定上限，路由决定性价比`

## 第 5 页｜本次比较口径：统一基准，避免数据看起来很乱

**内容**
- 为了让团队成员和领导更容易形成直觉，本次统一采用：
  - **Claude Sonnet 4.6 作为日常开发基准模型**
- 选择 Sonnet 4.6 作为基准的原因：
  - 编码能力强，社区认可度高
  - 日常开发适配度高
  - 价格和质量相对均衡
  - 非常适合作为“业务开发默认参照物”
- 统一口径：
  - **价格基准**：Sonnet 4.6 = **1.00x**
  - **速度基准**：Sonnet 4.6 的 TTFT 和输出速度作为比较参照
  - **能力基准**：在“日常业务开发”场景下，Sonnet 4.6 视作 **A 档基准**
- 本文价格对比采用一个标准工作负载：
  - **1M 输入 + 0.3M 输出**
  - 这样比单看输入价或输出价更接近日常编码场景

**辅助图建议**

**内容**

| 工具 | 定位 | 最强项 | 主要短板 | 公开成本信息 | 更适合谁 |
|---|---|---|---|---|---|

| Trae | 低成本 AI IDE | 低门槛试点、成本友好、快速起步 | 企业成熟度、价格口径、长期稳定性不如前两者清晰 | 官方站点公开信息偏免费；第三方资料有低价 Pro 说法 | 预算敏感团队、试点团队、个人开发者 |
| CodeBuddy | 国内企业 AI IDE / 插件体系 | VS Code / JetBrains 适配、企业知识库、SSO、模型配置、国产合规路线 | 国际社区最佳实践和生态声量弱于 Cursor；复杂自主代理口碑不如 Claude Code | 免费版 250 积分/2 周；Pro 约 $9.95/月；企业旗舰版 78 元/人/月；专享版 158 元/人/月 | 国内企业团队、强合规团队、知识库驱动研发 |
| OpenCode | 开源 AI coding agent / 桌面与扩展 | 开源免费、75+ provider、支持本地模型、可定制、隐私与自控强 | IDE 一体化精致体验和开箱即用治理弱于商业产品；需要自建规则和运维 | 工具本身免费；成本来自外部 API、模型费用或本地算力与运维 | 平台团队、隐私敏感团队、开源偏好团队、自带模型团队 |

  - **CodeBuddy 的最大价值在国内企业治理、知识库和合规落地**
  - **OpenCode 的最大价值在开源自控、模型自由度和本地化部署**

## 第 9 页｜速度对比：要分“交互延迟”和“持续吞吐”两件事看

**内容**
- 交互体感主要看：
  - **TTFT（首字延迟）**：开始回你第一批字要多久
  - **输出速度（tokens/s）**：开始回答后，能有多快持续生成
- 注意：速度数据受 provider 影响很大，适合看分层，不适合看绝对值

| 模型 | 公开 TTFT 参考 | 相对 Sonnet TTFT | 公开输出速度参考 | 相对 Sonnet 输出速度 |
|---|---:|---:|---:|---:|
| Claude Sonnet 4.6 | 0.98s | 1.00x | 42.7 tok/s | 1.00x |
| Claude Opus 4.6 | 1.2-1.9s | 1.2x-1.9x 更慢 | 40-42 tok/s | 0.94x-0.98x |
| GPT-5.3-Codex | 91.77s | 93.6x 更慢 | 62.7 tok/s | 1.47x |
| Gemini 2.5 Pro | 22-26s | 22x+ 更慢 | 116-133 tok/s | 2.7x-3.1x |
| Gemini 2.5 Flash | 0.52-0.53s | 0.53x 更快 | 195-222 tok/s | 4.6x-5.2x |
| GLM-5 | 0.79-1.39s | 0.8x-1.4x | 93-188 tok/s | 2.2x-4.4x |
| MiniMax M2.5 | 0.43-3.26s | 波动大 | 49-397 tok/s | 波动大 |

- 关键结论：
  - **GPT-5.3-Codex 的问题不在持续输出速度，而在首字延迟很高**
  - **它更适合长链路工程任务，不适合拿来做日常高频即时问答**
  - **Gemini Flash 非常适合高频交互与低成本批量任务**
  - **Gemini Pro 的价值在大上下文，不在日常交互爽感**
  - **GLM / MiniMax 速度很大程度取决于接入 provider**

  - 右图：输出速度越高越好

## 第 11 页｜真正实用的原则：不要押宝“唯一模型”，而要做“任务路由”

**内容**
- 日常研发最容易踩的坑：
  1. **拿最贵模型做所有任务** -> 成本很快失控
  2. **拿最便宜模型做所有任务** -> 复杂任务失败率高
  3. **只看 benchmark，不看实际流程** -> 落地效果差
- 更合理的策略是三层路由：
  - **第一层：低成本快响应**
    - 用于草稿、批量生成、低风险任务
    - 推荐：Gemini Flash / MiniMax M2.5
  - **第二层：日常主力**
    - 用于 feature、bugfix、测试、review
    - 推荐：Sonnet 4.6 / GLM-5-Code
  - **第三层：复杂攻坚**
    - 用于大重构、遗留系统、复杂规划
    - 推荐：Opus 4.6 / Claude Code / GPT-5.3-Codex
- 这比“全员一把梭某个最强模型”更容易兼顾：
  - 体验
  - 成本
  - 成功率

**辅助图建议**
- 决策流程图：
  - 任务是否高风险？
  - 是否需要长上下文？
  - 是否中文文档密集？
  - 是否批量低成本？

## 第 17 页｜最终选型方案 C / D / E：性价比、国内企业治理、开源自控

- **工作台**：CodeBuddy
- **主力模型**：企业内置或自定义模型路由
- **国内优先组合建议**：GLM-5-Code / MiniMax M2.5 等兼容模型

- 国内采购、合规和落地沟通成本更低

- **工作台**：OpenCode
- **模型策略**：自带 API key 或本地模型

  - 日常主力：Sonnet 4.6 / GLM-5-Code

- 模型自由度最高

**风险**

## 第 19 页｜给团队和领导的建议：如何分阶段落地，而不是一次性押注

**内容**
- 推荐用 **3 个阶段** 落地，而不是一次性全量采购：

### 第 1 阶段：4 周试点
- 先选 1~2 个小组
- 默认组合：**Cursor + Sonnet 4.6**
- 若团队有强合规诉求，可同步小范围试点：**CodeBuddy + 国内模型路由**
- 若团队有强自控诉求，可同步小范围试点：**OpenCode + 自带模型**
- 观察：
  - 首版产出时间
  - bug 定位时间
  - 测试补齐效率
  - 使用频率

### 第 2 阶段：加入路由
- 把任务按难度分层：
  - 低风险：Flash / MiniMax
  - 日常主力：Sonnet / GLM
  - 高风险：Opus / Claude Code / GPT-5.3-Codex
- 建立内部最佳实践：
  - 哪类任务用哪个模型
  - 哪些提示词模板最好用
  - 哪些场景必须人工复核
  - 哪些团队适合 Cursor / CodeBuddy / OpenCode 三种工作台

### 第 3 阶段：以 ROI 决策扩容
- 建议团队和领导一起看 5 个指标：
  1. 需求到 PR 的 lead time
  2. 平均修复时长
  3. 单测补齐率 / 覆盖率提升
  4. bug reopen / 回归问题变化
  5. 人均 AI 成本

- 推荐管理原则：
  - **不强行统一唯一模型**
  - **统一工作台 + 统一路由规范**
  - **高风险代码必须保留人工 review 和自动化测试**

**辅助图建议**
- 三阶段路线图：试点 -> 路由 -> 扩容
- 右侧放一个 ROI 仪表盘示意
